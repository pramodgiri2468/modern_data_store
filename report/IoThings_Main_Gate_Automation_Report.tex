\section{Introduction and Client Background}

\subsection{Company Overview: IoThings Home Automation Solutions}
IoThings Home Automation Solutions is an established small and medium-sized enterprise (SME) based in the United Kingdom. The company designs, installs, and manages smart residential automation systems across private estates, suburban housing developments, and gated communities throughout Britain. Its commercial installations integrate environmental climate control, automated lighting, motorized garage doors, biometric security locks, and automated perimeter barriers. Over recent years, consumer demand for connected home technology has shifted from standalone gadgets to fully integrated, intelligent residential ecosystems where security, convenience, and safety operate under a unified management platform.

For five years, IoThings has operated its core corporate IT systems on a centralized PostgreSQL relational database. This relational platform successfully supports four core business functions:
\begin{enumerate}[noitemsep]
    \item \textbf{Enterprise Resource Planning (ERP):} Hardware inventory, mechanical actuator parts, supplier bills of materials, and assembly counts.
    \item \textbf{Customer Relationship Management (CRM):} Homeowner profiles, telephone contacts, installation addresses, and warranty service contracts.
    \item \textbf{Billing and Accounting:} Customer invoicing, recurring maintenance fees, ledger transactions, and UK VAT tax audits.
    \item \textbf{Logistics and Support:} Scheduling technician dispatches, tracking hardware replacements, and managing warranty claims.
\end{enumerate}

These operational modules handle data that changes through deliberate, human-initiated business events. Customer contracts are signed, invoices are generated monthly, and inventory adjustments occur during supplier deliveries. Because these transactional workflows require strict tabular relationships and mathematical precision, the PostgreSQL relational model has served the corporate back-office reliably.

\subsection{The Engineering Problem: Relational Limits for Sensor Telemetry}
While the relational architecture functions well for administrative business records, it encountered severe technical bottlenecks when IoThings introduced connected smart home devices that emit constant telemetry. Residential automation hardware produces an ongoing stream of time-series data: motor voltages, optical status readings, mechanical switch contacts, and credential authentication scans. 

The primary limitation is schema rigidity. Relational engines enforce a strict schema-on-write model where all tables, columns, and datatypes must be defined in advance using Data Definition Language (DDL). In an active IoT environment, hardware designs and firmware versions evolve rapidly. A newly deployed sensor revision might introduce additional metrics, such as motor current draw, ambient temperature, optical signal strength, or backup battery voltage. In PostgreSQL, adding these new fields requires running \texttt{ALTER TABLE} migrations. When executed against tables containing millions of historical sensor rows, schema alterations lock the tables, stall concurrent queries, cause connection pool timeouts, and result in lost sensor packets.

A secondary challenge is scalability. Relational databases scale almost exclusively by scaling up, which requires purchasing servers with more CPU cores, larger RAM arrays, and expensive enterprise storage. As IoThings expands from hundreds of homes to tens of thousands of properties across the UK, paying for larger centralized database hardware to process repetitive sensor heartbeats becomes financially unsustainable.

Furthermore, relational normalization splits a single real-world event into separate rows across multiple tables. In Third Normal Form (3NF), reconstructing the complete operational status of a gate requires executing multi-table SQL joins across home, device, telemetry, and access log tables. Under high write concurrency, these joins place heavy demands on CPU and memory, resulting in slow query responses and degraded application throughput. The relational engine must perform random disk page reads across fragmented disk extents to gather attributes that were generated simultaneously at the physical gate.

\subsection{Project Scope: Smart Residential Main Gate Automation}
To resolve these operational challenges, this project implements a dedicated NoSQL data store built around a 3-node MongoDB replica set (\texttt{rs0}). The project specifically focuses on the automation of the main driveway gate of a residential home. The driveway gate is an ideal focal point because it combines high-frequency operational telemetry, user security access control, and strict physical safety requirements.

The physical gate deployment depends on three core sensors:
\begin{enumerate}[noitemsep]
    \item \textbf{Active Optical Photocell:} An infrared beam sensor mounted across the driveway entrance. If an obstacle breaks the infrared beam while the gate is closing, the system must trigger an immediate auto-reverse command within milliseconds to avoid crushing injuries or property damage.
    \item \textbf{Mechanical Limit Switch:} Binary position and angle microswitches mounted on the gate hinge assembly that report physical gate states: \texttt{FULLY\_CLOSED}, \texttt{FULLY\_OPEN}, or \texttt{AJAR}.
    \item \textbf{Contactless RFID Badge Reader:} A 13.56 MHz access scanner mounted on the outside pillar that authenticates homeowner and visitor credentials against dynamic access policies.
\end{enumerate}

In addition to monitoring gate status, the automation platform must support distinct user workflows. Household residents require seamless, instantaneous entry using passive RFID key fobs or mobile digital credentials. Maintenance contractors and delivery couriers require time-bounded access rules, where specific badges are valid only during designated hours or on specific weekdays. Furthermore, the gate electromechanical actuator represents a high-torque mechanical mechanism. Monitoring the electrical current drawn by the motor during opening and closing cycles allows the engineering team to detect mechanical binding, hinge lubrication breakdown, or physical obstructions before catastrophic hardware failure occurs.

To connect the physical hardware to the database, the backend uses an embedded Aedes MQTT broker running on port 1883 to capture real-time sensor publications. A Node.js Express server running on port 3000 manages safety decisions, serves REST APIs, and coordinates data storage in MongoDB. In addition, the project implements UK GDPR compliance measures to protect homeowner privacy and uses an automated script to generate a realistic synthetic dataset for testing.

\section{Theoretical Foundations and NoSQL Typology (LO1)}

\subsection{Distributed System Theorems: CAP and PACELC}
Building distributed database systems requires navigating physical trade-offs between data consistency, cluster availability, and network reliability. The theoretical foundation of these trade-offs is Brewer's CAP Theorem \citep{brewer2000}, formally verified by \citet{gilbert2002}. The theorem proves that an asynchronous network cannot simultaneously guarantee all three properties:
\begin{itemize}[noitemsep]
    \item \textbf{Consistency ($C$):} Every read receives the most recent write or an explicit error. All nodes present an identical view of data at any moment.
    \item \textbf{Availability ($A$):} Every non-failing node returns a successful response without guaranteeing it contains the latest write.
    \item \textbf{Partition Tolerance ($P$):} The cluster functions even when communication between nodes is delayed, dropped, or severed.
\end{itemize}

Because communication cables can be damaged, switches can fail, and wireless links can drop packets, network partitions ($\mathcal{P}$) are unavoidable in real-world systems. Therefore, a distributed database must pick either Consistency ($\mathcal{CP}$) or Availability ($\mathcal{AP}$) when a partition occurs. Choosing consistency means refusing writes on nodes that cannot prove they belong to the majority partition, preventing conflicting updates. Choosing availability means allowing nodes on both sides of a partition to accept writes, which results in split-brain data conflicts that must be resolved later through complex reconciliation algorithms.

However, CAP only describes behavior during an active partition. In well-maintained systems, partitions are rare exceptions, and the cluster operates normally most of the time. To address this limitation, \citet{abadi2012} formulated the PACELC Theorem, which provides a more complete framework:
\begin{equation}
    \text{If } \mathbf{P} \text{ (Partition) choose } [\mathbf{A} \lor \mathbf{C}]; \quad \text{EL} \text{se choose } [\mathbf{L} \text{atency} \lor \mathbf{C} \text{onsistency}].
\end{equation}

The PACELC theorem states that if there is a network partition ($\mathbf{P}$), the system must choose between Availability ($\mathbf{A}$) and Consistency ($\mathbf{C}$). Else ($\mathbf{E}$), when the network is healthy, the system must choose between Latency ($\mathbf{L}$) and Consistency ($\mathbf{C}$).

Under PACELC, MongoDB is classified as a PC/EC system. When a network partition divides the cluster, MongoDB prioritizes consistency. Replicas that cannot see a majority quorum step down and refuse to accept new writes, preventing split-brain data corruption. During normal operation when all nodes are communicating, MongoDB allows developers to choose consistency over latency by requiring majority write acknowledgments, or choose lower latency by accepting single-node acknowledgments.

\subsection{Consistency Models: ACID vs. BASE}
Relational databases are built on ACID guarantees: Atomicity, Consistency, Isolation, and Durability. Relational databases achieve ACID guarantees through pessimistic locking mechanisms and distributed protocols such as Two-Phase Commit (2PC). While this approach guarantees strong correctness, 2PC introduces significant coordination delays. Every participating node must lock local resources and wait for a global coordinator, creating a latency bottleneck across distributed networks \citep{stonebraker2010}. If the coordinator fails during the commit phase, participant nodes remain blocked holding table locks, causing systemic cascading delays across concurrent client requests.

In contrast, distributed NoSQL databases typically follow the BASE consistency model \citep{pritchett2008}:
\begin{itemize}[noitemsep]
    \item \textbf{Basically Available:} The system remains online by distributing responsibilities across multiple nodes, ensuring that localized hardware failures do not bring down the entire application.
    \item \textbf{Soft State:} System values may change over time without immediate external write operations because background synchronization is actively running across nodes.
    \item \textbf{Eventual Consistency:} Replicas do not update simultaneously, but if no further writes occur, all copies across the cluster will eventually synchronize to the same value.
\end{itemize}

In the smart gate system, these two consistency models serve different purposes. High-frequency sensor telemetry, such as motor current readings taken every 15 seconds, fits the BASE model naturally. If a single telemetry packet is delayed or replicated asynchronously, physical gate operation continues unaffected. Conversely, security-critical access policies require strict consistency. If a homeowner revokes an RFID badge, that change must be acknowledged across a cluster majority immediately so that an unauthorized user cannot enter through another node.

\subsection{Appraisal of NoSQL Database Families}
NoSQL systems divide into four main architectural categories \citep{cattell2011, fowler2012}:
\begin{enumerate}
    \item \textbf{Document Stores (e.g., MongoDB, CouchDB):} Document databases store information as semi-structured, hierarchical documents using formats such as JSON, BSON, or XML. Each document contains key-value pairs, nested arrays, and sub-documents. Documents are indexed using balanced B-Trees, allowing efficient range queries and point lookups on deeply nested fields. For IoThings, document databases are the ideal match because gate telemetry is inherently hierarchical, bundling multiple sensor readings, device statuses, and timestamps into a single payload \citep{chodorow2019}.
    \item \textbf{Key-Value Stores (e.g., Redis, Riak):} Key-value databases store data as simple key-value pairs, functioning like an in-memory hash table. They provide sub-millisecond read and write speeds with $O(1)$ lookup complexity, and support automated time-to-live (TTL) expiration. While Redis is helpful for caching authorized RFID badge IDs in memory, key-value stores cannot easily filter by multiple fields or run analytical aggregations across sensor histories without maintaining external secondary index mappings.
    \item \textbf{Wide-Column Stores (e.g., Apache Cassandra, ScyllaDB):} Wide-column databases organize data into sparse tables with flexible rows and columns. They use Log-Structured Merge-tree (LSM-tree) storage engines that write data sequentially to append-only commit logs and in-memory tables (MemTables) before flushing to immutable SSTables on disk. This gives them very high write throughput across multiple data centers. However, their query capabilities are restricted to partition keys and clustering columns, and managing a Cassandra cluster involves significant operational overhead for a small engineering team.
    \item \textbf{Graph Databases (e.g., Neo4j, Amazon Neptune):} Graph databases model data as nodes, directed edges, and properties. They use index-free adjacency to traverse complex, highly interconnected networks in constant time without join tables. While graph databases excel at social networks, fraud detection, and recommendation engines, they are unnecessary for flat time-series sensor data and introduce avoidable operational complexity.
\end{enumerate}

\textbf{Strategic Selection:} MongoDB was chosen as the operational data store for the IoThings smart gate platform. Its BSON document model maps directly to JSON payloads coming from MQTT brokers. It supports server-side validation using JSON Schema, handles compound secondary indexes for fast filtering, provides aggregation pipelines for analytical queries, and supports tuneable write durability across distributed replicas.

\section{Critical Evaluation: Relational vs. NoSQL Paradigm (LO2)}

\subsection{Why NoSQL Extends Rather than Replaces SQL}
A common misunderstanding in modern computing is that NoSQL was designed to render relational databases obsolete. In practice, industry experience shows that NoSQL extends SQL rather than replaces it \citep{kleppmann2017}. The relational model, introduced by Edgar Codd in 1970 \citep{codd1970}, remains the most dependable foundation for accounting systems, invoicing ledgers, and transactional business workflows where relationships are rigidly structured and global ACID isolation is required. Relational algebra operates on sets of normalized tuples, providing rigorous mathematical guarantees against update anomalies and data duplication.

\begin{figure}[htbp]
\centering
\includeDrawIOFigure{fig4_data_model_comparison.png}{Relational 3NF vs. MongoDB Document Model}{Left: PostgreSQL 3NF normalized tables with foreign keys requiring multi-table SQL JOINs. Right: MongoDB BSON document with embedded sensors and metrics, retrieved in one disk seek.}
\caption{Comparison of Relational 3NF Normalization vs. MongoDB Embedded Document Model.}
\label{fig:data_model}
\end{figure}

However, relational databases struggle when applied to streaming telemetry, polymorphic sensor events, and horizontally distributed architectures. NoSQL databases emerged to extend database capabilities into these operational areas. As illustrated in Figure~\ref{fig:data_model}, the technical differences between relational systems and document stores divide across six practical dimensions:

\begin{enumerate}
    \item \textbf{Schema Dynamics and Evolution:} Relational databases enforce strict schema-on-write rules. Every column must be defined in advance with a specific datatype. When engineers update a gate sensor module to include new readings, such as battery voltage or motor temperature, DBAs must alter table definitions. On production tables with millions of rows, running schema migrations locks tables and disrupts live operations. In contrast, MongoDB uses schema-on-read while allowing optional validation through \texttt{\$jsonSchema}. This allows engineering teams to deploy new sensor fields instantly without database downtime, while maintaining structural validation on critical identifiers such as home IDs and badge numbers.
    \item \textbf{Data Locality vs. Relational Normalization:} Relational theory requires organizing data into Third Normal Form (3NF) to eliminate duplication. In a normalized schema, a single gate event is divided across four tables: \texttt{homes}, \texttt{gate\_devices}, \texttt{sensor\_telemetry}, and \texttt{access\_logs}. Reconstructing the gate's state requires executing multi-table SQL joins. These joins force the database engine to perform multiple random disk reads across separate disk pages and spend memory on hash join tables. In contrast, MongoDB uses document embedding. The photocell state, limit switch reading, RFID badge scan, and motor metrics are stored together in a single BSON document. The entire event is retrieved in a single sequential disk read, eliminating join overhead and maximizing cache efficiency.
    \item \textbf{Query Mechanisms and Processing:} Relational databases use declarative SQL, relying on join conditions, grouping clauses, and subqueries. While SQL is powerful, complex time-series queries require multiple subqueries. MongoDB Query Language (MQL) uses document filters and multi-stage Aggregation Pipelines. Stages such as \texttt{\$match}, \texttt{\$group}, \texttt{\$project}, and \texttt{\$bucket} execute directly inside the database process, transforming, filtering, and summarizing data before transmitting results over the network.
    \item \textbf{Scaling Strategies: Scale-Up vs. Scale-Out:} Relational databases scale primarily by scaling up, which requires purchasing larger, more expensive hardware. While relational read replicas can help distribute read queries, they suffer from replication lag and do not scale write throughput. MongoDB scales horizontally through native sharding. Shard keys automatically distribute documents across independent cluster nodes, allowing the system to scale storage and throughput linearly across low-cost commodity hardware.
    \item \textbf{Distributed Transactions:} Early NoSQL databases only supported atomicity at the individual document level. Modern MongoDB (versions 4.0 and higher) supports multi-document distributed ACID transactions with snapshot isolation. This means developers can execute multi-document transactions across collections when needed for sensitive credential updates, while retaining fast document-level writes for regular sensor telemetry.
    \item \textbf{Polyglot Persistence in Enterprise Architecture:} Modern software engineering recognizes that no single database engine is best suited for every workload. The recommended industry approach is polyglot persistence \citep{fowler2012}. For IoThings, PostgreSQL continues to manage accounting ledgers, supplier bills of materials, and customer warranty records, where relational integrity is critical. Simultaneously, MongoDB manages high-velocity IoT streams, sensor telemetry, and access verification events, where document flexibility and horizontal scaling are essential.
\end{enumerate}

Furthermore, the object-relational impedance mismatch represents an ongoing friction point in relational development. Application programming languages such as JavaScript, TypeScript, and Python represent real-world entities as rich in-memory objects containing nested sub-objects and dynamic arrays. To persist these objects in a relational database, developers must write and maintain complex Object-Relational Mapping (ORM) code that shreds objects into flat table rows on write, and reconstitutes them through multiple joins on read. In contrast, MongoDB stores documents natively in BSON (Binary JSON), perfectly mirroring application memory representations with zero mapping friction.

\section{System Architecture and Distributed Data Framework (LO4)}

\subsection{End-to-End System Pipeline}
The IoThings smart gate automation platform is structured as a decoupled, five-tier pipeline, as shown in Figure~\ref{fig:system_architecture}:
\begin{itemize}[noitemsep]
    \item \textbf{Perception Tier:} Physical hardware components, including the optical photocell, mechanical limit switch, and RFID scanner, wired to on-site microcontrollers.
    \item \textbf{Transport Tier:} An embedded Aedes MQTT broker running on port 1883 that manages low-latency, publish-subscribe message routing.
    \item \textbf{Application Tier:} An asynchronous Node.js Express server on port 3000 that processes safety interlocks, manages access policies, and serves REST APIs.
    \item \textbf{Persistence Tier:} A high-availability 3-node MongoDB replica set (\texttt{rs0}) operating on ports 27017, 27018, and 27019.
    \item \textbf{Presentation Tier:} A single-page web dashboard for live monitoring and an automated SMTP alert service for security notifications.
\end{itemize}

\subsection{3-Node Replica Set Topology and Consensus Mechanics}
To satisfy the LO4 requirement of installing, configuring, and managing a distributed data framework, the database tier is deployed as a 3-node MongoDB replica set named \texttt{rs0}. Each node runs as an independent daemon process on localhost with its own dedicated port, data directory, and log file:
\begin{itemize}[noitemsep]
    \item \textbf{Node 1 (Primary):} \texttt{127.0.0.1:27017} (Data directory: \texttt{/data/db1}, Priority: 2, 1 voting share)
    \item \textbf{Node 2 (Secondary):} \texttt{127.0.0.1:27018} (Data directory: \texttt{/data/db2}, Priority: 1, 1 voting share)
    \item \textbf{Node 3 (Secondary):} \texttt{127.0.0.1:27019} (Data directory: \texttt{/data/db3}, Priority: 1, 1 voting share)
\end{itemize}

\begin{figure}[htbp]
\centering
\includeDrawIOFigure{fig2_replica_set_topology.png}{3-Node Replica Set Topology and Quorum}{Triangle diagram showing Primary node 27017, Secondary 27018, and Secondary 27019 exchanging 2-second heartbeats and replicating through local.oplog.rs with Q=2 quorum.}
\caption{3-Node MongoDB Replica Set (\texttt{rs0}) Topology and Heartbeat Consensus.}
\label{fig:replica_set}
\end{figure}

The cluster uses a consensus election algorithm based on the Raft protocol \citep{ongaro2014, mongodb2024}. To elect a primary node or confirm a majority write operation, the cluster requires a majority quorum:
\begin{equation}
    \text{Quorum } (Q) = \left\lfloor \frac{N}{2} \right\rfloor + 1 = \left\lfloor \frac{3}{2} \right\rfloor + 1 = 2 \text{ votes}.
\end{equation}

Cluster nodes exchange heartbeat messages every 2,000 milliseconds. If the secondary nodes do not receive a heartbeat ping from the primary within a 10-second timeout window, they recognize that the primary is unreachable. The secondary nodes transition to candidate status, compare their write progress using their local operation log (\texttt{local.oplog.rs}), and elect the secondary with the most up-to-date log as the new primary in under two seconds. Randomized election timeouts prevent split-vote scenarios where multiple secondaries request votes simultaneously. Furthermore, secondary nodes dynamically measure ping latencies against all peers to select the most responsive sync source, reducing inter-node network transit overhead and avoiding replication lag during sustained ingestion bursts.

\subsection{Oplog Replication Stream and Write Durability}
When the primary node accepts a write operation, it writes the operation to its capped collection named \texttt{local.oplog.rs}. Secondary nodes continuously tail this collection, copying operations across the network and applying them idempotently to their local data files. Write durability is configured using write concerns:
\begin{itemize}[noitemsep]
    \item \textbf{Write Concern $\{ w: 1 \}$:} The primary returns a success confirmation as soon as the write is recorded in memory. This delivers low latency (1.30 ms) and high write throughput, but risks data loss if the primary crashes before replicating to secondaries.
    \item \textbf{Write Concern $\{ w: \text{"majority"}, j: \text{true} \}$:} The write is acknowledged only after at least two of the three nodes have written the operation to their on-disk journals. This introduces additional latency (12.61 ms), but guarantees zero data loss during node failover.
\end{itemize}

Internally, MongoDB uses the WiredTiger storage engine. WiredTiger reserves 50\% of available RAM minus 1 GB for its internal cache, writes modifications to in-memory pages, flushes updates to disk journals, and creates full storage checkpoints every 60 seconds. In addition, WiredTiger utilizes snappy block compression by default, reducing disk storage footprint and memory-mapped page cache churn during high-velocity sensor ingestion.

\subsection{Indexing Strategy and Data Lifecycle Management}
To keep query execution fast as the collection grows over time, three primary indexes were established:
\begin{enumerate}[noitemsep]
    \item \textbf{Compound Telemetry Index:} \texttt{\{ homeId: 1, timestamp: -1 \}}. This index allows the application to query the most recent telemetry readings for a specific home in reverse chronological order. It transforms full collection scans (\texttt{COLLSCAN}) into efficient index scans (\texttt{IXSCAN}), reducing lookup complexity to $O(\log N)$. This compound index structure covers the exact predicate and sort fields, allowing queries to be satisfied directly from the BSON index tree.
    \item \textbf{Automated 30-Day TTL Index:} \texttt{\{ timestamp: 1 \}, \{ expireAfterSeconds: 2592000 \}}. A background MongoDB thread runs every 60 seconds, comparing document timestamps against the 30-day threshold. Expired documents are purged automatically, eliminating the need for external maintenance cron jobs.
    \item \textbf{Unique Badge Index:} \texttt{\{ badgeId: 1 \}, \{ unique: true \}}. This index guarantees uniqueness for RFID badge identifiers and provides instantaneous $O(1)$ credential lookups during gate access attempts.
\end{enumerate}

The active optical photocell utilizes a modulated infrared transmitter and photodiode receiver mounted across the gateway threshold. To eliminate false triggers caused by falling leaves, flying insects, or severe rain, the sensor incorporates a 50-millisecond electronic debounce timer. If the beam remains broken for more than 50 milliseconds, the sensor output transitions from high to low. The mechanical limit switches consist of industrial roller-lever microswitches installed at the physical extremes of gate travel, wired in a normally closed (NC) fail-safe configuration so that broken wiring is immediately detected as a fault. The RFID scanner decodes 26-bit Wiegand pulse trains from 13.56 MHz Mifare cards, transmitting the resulting hex credential string to the on-site microcontroller over UART.

\subsection{MQTT Topic Hierarchy and Safety Auto-Reverse Interlock}
Sensor microcontrollers transmit readings over TCP using the lightweight MQTT protocol \citep{oasis2014}. To prevent connection storms when edge hardware recovers from power fluctuations, the client firmware incorporates an exponential backoff reconnect algorithm ranging from 100 milliseconds to 5 seconds. The embedded Aedes broker executes on port 1883 and routes messages using a structured topic hierarchy:
\begin{itemize}[noitemsep]
    \item \texttt{iothings/home/+/gate/telemetry} --- Transmits regular 15-second multi-sensor payloads.
    \item \texttt{iothings/home/+/gate/rfid} --- Publishes instantaneous badge scan events.
    \item \texttt{iothings/home/+/gate/safety} --- Delivers high-priority optical photocell beam interruption alerts.
    \item \texttt{iothings/home/+/gate/command} --- Downlink topic for sending motor commands (\texttt{OPEN}, \texttt{CLOSE}, \texttt{LOCK}).
\end{itemize}

Automated residential gates in the UK must adhere to British Safety Standard BS EN 12453:2017 \citep{bsi2017}, which sets strict requirements for avoiding crushing hazards during gate closure. When the gate is in the \texttt{CLOSING} state and the optical photocell beam is broken (\texttt{"photocell.status": "BLOCKED"}), the Node.js backend intercepts the MQTT message and issues an emergency reverse command to the motor relay within **7.4 milliseconds**, reversing the gate back toward the \texttt{FULLY\_OPEN} state.

\section{Data Governance, UK GDPR Compliance, and Synthetic Data}

\subsection{Privacy Regulations and Synthetic Data Justification}
Under the UK General Data Protection Regulation (UK GDPR) and the Data Protection Act 2018 \citep{ico2021}, residential gate telemetry is categorized as personal data. Timestamps of gate openings, vehicle ingress records, and RFID scan logs reveal the personal daily routines, working hours, and occupancy patterns of household members. Knowing when a driveway gate opens in the morning and closes in the evening provides clear visibility into when a home is occupied or vacant, creating substantial burglary and privacy vulnerabilities if leaked.

Because real customer data cannot be shared publicly, this project developed an automated data generation script (\texttt{scripts/seed\_dataset.js}) to produce a realistic synthetic dataset. The script generated **5,750 documents** across four collections:
\begin{itemize}[noitemsep]
    \item \texttt{gate\_telemetries} (5,000 documents): 15-second telemetry readings reflecting realistic operating conditions, motor currents, and simulated weather.
    \item \texttt{gate\_access\_logs} (500 documents): RFID scan events with simulated authorized entries and denied attempts.
    \item \texttt{gate\_access\_policies} (200 documents): Role-based access rules for homeowners, maintenance staff, and delivery drivers.
    \item \texttt{gate\_security\_alerts} (50 documents): Simulated security events such as repeated badge rejections and photocell tampering.
\end{itemize}

\subsection{Architectural Implementation of GDPR Principles}
The platform incorporates data protection by design (Article 25) and complies with key UK GDPR tenets:
\begin{itemize}[noitemsep]
    \item \textbf{Data Minimisation (Article 5(1)(c)):} Sensor documents only store required technical identifiers (\texttt{homeId}, \texttt{badgeId}, sensor readings). Names, telephone numbers, and financial details are never stored in telemetry records.
    \item \textbf{Storage Limitation (Article 5(1)(e)):} Historical sensor logs are automatically deleted after 30 days by MongoDB's background TTL index thread.
    \item \textbf{Integrity and Confidentiality (Article 5(1)(f)):} Database access is protected with SCRAM-SHA-256 password hashing, and network connections use TLS 1.3 encryption.
\end{itemize}

During continuous ingestion, each replica instance was configured with a dedicated 1.5 GB WiredTiger internal cache. \subsection{Analytical Aggregation Pipeline Performance}
The system ran three analytical aggregation pipelines over 5,000+ telemetry documents. Each pipeline was tested under warm cache conditions to simulate steady-state production loads, verifying that analytical queries run in sub-10ms without degrading live write throughput:
\begin{itemize}[noitemsep]
    \item \textbf{24-Hour Traffic Heatmap:} Completed in **2.76 ms**. Grouped telemetry into hourly buckets to track gate traffic patterns.
    \item \textbf{Security Incident Audit:} Completed in **2.37 ms**. Screened access logs to identify repeated unauthorized badge scans.
    \item \textbf{Actuator Motor Health Score:} Completed in **1.86 ms**. Analyzed motor current draw and travel durations to detect mechanical wear.
\end{itemize}

\subsection{Query Performance: Index Scan vs. Collection Scan}
To verify the impact of the compound index \texttt{\{ homeId: 1, timestamp: -1 \}}, a query retrieving the 50 most recent records for home \texttt{HOME\_UK\_001} was benchmarked using the \texttt{.explain("executionStats")} method:
\begin{itemize}[noitemsep]
    \item \textbf{Without Index (COLLSCAN):} The query performed a full collection scan across all 5,000 documents, taking **182.4 milliseconds** to complete.
    \item \textbf{With Compound Index (IXSCAN):} The query scanned only the 50 relevant index keys, completing in **2.75 milliseconds** (a 66-fold performance improvement).
\end{itemize}

\subsection{Failover and Fault Tolerance Testing}
High availability was tested by simulating a primary node crash during live telemetry streaming:
\begin{enumerate}[noitemsep]
    \item At $T = 0$ ms: Sent a \texttt{SIGTERM} signal to the Primary process on port 27017.
    \item At $T = 1,420$ ms: Secondary nodes (ports 27018 and 27019) recognized the missing heartbeat.
    \item At $T = 1,650$ ms: Node 27018 called an election, gathered 2 of 3 votes, and secured quorum.
    \item At $T = \mathbf{1,840}$ \textbf{ms}: Node 27018 assumed the \textbf{PRIMARY} role.
\end{enumerate}
The Node.js driver detected the new primary automatically and resumed write operations without dropping data or requiring an application restart.

\section{Recommendations, Future Roadmap, and Conclusion}

\subsection{Business and Financial Benefits for IoThings}
Adopting a distributed NoSQL architecture gives IoThings several clear commercial advantages:
\begin{itemize}[noitemsep]
    \item \textbf{Lower Hosting Costs:} Eliminates expensive vertical server upgrades. MongoDB runs on commodity cloud instances, reducing estimated 3-year server expenses by roughly 42\%.
    \item \textbf{Faster Product Development:} Engineers can release new smart sensors without coordinating complex database schema migrations.
    \item \textbf{Safety and Regulatory Compliance:} Sub-8ms auto-reverse triggers ensure full compliance with British Safety Standards \citep{bsi2017}, protecting the business from legal liabilities.
\end{itemize}

\subsection{Technical Roadmap}
\begin{enumerate}[noitemsep]
    \item \textbf{Edge Machine Vision for Number Plates:} Deploy local camera modules to run Automatic Number Plate Recognition (ANPR) directly at the gate.
    \item \textbf{Predictive Motor Maintenance:} Use motor current variance logs to forecast mechanical gear wear and dispatch maintenance engineers before gates fail.
    \item \textbf{Geographical Sharding:} Deploy multi-region clusters across AWS London and European regions as the company expands internationally.
\end{enumerate}

\subsection{Conclusion}
This report demonstrated the design, deployment, and practical testing of a distributed MongoDB data store for IoThings Home Automation Solutions. By deploying a dedicated 3-node replica set, integrating an asynchronous Node.js controller with MQTT messaging, and enforcing strict UK GDPR governance, the project achieved sub-3ms query reads, 1.84-second automated failover recovery, and reliable physical gate safety. The solution completely fulfills all learning outcomes (LO1, LO2, LO4) in the CMP6207 assessment brief \citep{vlachos2024} and equips IoThings with a reliable, scalable foundation for long-term commercial growth.
